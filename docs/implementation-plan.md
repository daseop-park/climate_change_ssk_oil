> ⚠️ **id 두 개가 이름과 어긋납니다.** 2026-08-12 개편에서
> `문화상품권 10,000원` → `배달앱 20,000원`, `배달앱 3,000원` → `배달앱 10,000원` 으로 바뀌었지만
> **id 는 그대로 뒀습니다.** id 는 이미 발급된 코드가 가리키는 키라, 바꾸면 새 상품 행이 생기고
> 기존 코드는 옛 상품에 매달린 채 남습니다. 등급·분배 수량은 그대로여서 합계 100% 는 유지됩니다.

화면 표기는 그래도 **발급 비율에서 계산**한다. 하드코딩하면 2차 배치에서 분배가 달라지는 순간
표기와 실제가 어긋납니다.

> 1등이 1개뿐이므로, 그 패드를 쓰지 않고 버리면 1등은 미청구로 남습니다.
> 사전 배정 모델의 알려진 한계이며 시연 목적에서는 감수합니다.

### 코드 형식 상세

- 문자셋: 영문 대문자에서 오독 위험 문자 **I·O 제외** (24자), 숫자에서 **0·1 제외** (8자)
- 공간: 24³ × 8³ = **7,077,888** 조합. 유효 코드 100개 → 약 **7.1만 회 시도당 1회 적중**
- **따라서 rate limiting은 선택이 아니라 필수다.** 제한이 없으면 초당 100요청으로 **약 12분**이면 뚫립니다.
  분당 5회/IP로 제한하면 평균 약 10일이 걸려 시연 기간 내에는 실질적으로 무의미해집니다
  (총량이 30 → 100으로 늘면서 적중까지 걸리는 시간도 1/3로 줄었습니다)
- `codeSchema` 정규식을 `^[A-Z]{3}-[0-9]{3}$`로 **좁힌다** (현재 `^[A-Z]+-[A-Z0-9]+$`)
- 입력 편의: 하이픈 없이 `ABC123`으로 쳐도 통과하도록 정규화 후 검증
- 배치가 커지면(수만 개) 유효 코드 밀도가 올라가 6자리로는 부족해집니다. **총량 1000개 초과 시 자릿수 재검토**

### 작업

### 발급 스크립트에서 놓치면 안 되는 것
1. **`crypto.randomInt` 사용.** 현재 `Math.random()`은 예측 가능해서 실발급에 부적합
2. **상품↔코드 배정 셔플.** 1등부터 순서대로 insert하면 DB 순서대로 인쇄했을 때 상자 앞쪽 패드가 전부 1등
3. **`@unique` 충돌 재시도.** 30개/700만 조합이라 확률은 낮지만 코드로 보장
4. **분배 합계 == 총량 검증.** 안 맞으면 실행 거부
5. 실행은 **멱등하지 않다.** 두 번 돌리면 60개가 됩니다. `--batch` 이름 필수 + 중복 배치 거부

### 1단계에서 실제로 겪은 문제 (모두 해결)
- **생성된 Prisma 클라이언트를 Node 로 직접 실행 불가** — 확장자 없는 상대 import 를 Node ESM 이 거부.
  `tsx` 를 devDependency 로 추가해 해결. 스크립트는 top-level await 대신 `main()` 래퍼를 씁니다
  (package.json 에 `"type": "module"` 이 없어 tsx 가 CJS 로 트랜스파일하기 때문)
- **`prisma migrate dev` 가 클라이언트를 재생성하지 않음** — `npx prisma generate` 를 별도 실행해야 했습니다.
  `postinstall` 스크립트로 상시 보장하도록 조치

## 2단계 — 읽기 API + 레이어 골격

**예상 2시간** (범위 1시간 45분 ~ 2시간 30분)

### 확정 방침 (2026-08-06 결정)

**1) 경품 데이터는 서버에서 렌더한다.** 클라이언트 `useQuery`로 가져오면 로딩 상태가 생기는데
핸드오프에 경품 그리드 스켈레톤이 없습니다. 루트 `layout.tsx`가 서버 컴포넌트인 점을 이용합니다.

```
layout.tsx (서버)  ── 경품 6종 조회 ──▶  <AppShell products={...}>
                                              ├ ShellContext 에 주입
                                              ├ PrizeSection  (context에서 읽음)
                                              └ PrizeSheet    (context에서 읽음)
```

그리드와 바텀시트가 같은 데이터를 공유하는 현재 구조가 그대로 유지되고 로딩 상태가 없습니다.
**대신 모든 라우트가 정적(`○`) → 동적(`ƒ`)으로 바뀝니다.** 6행 조회라 비용은 무시할 수준입니다.

**2) TanStack Query는 3단계로 미룬다.** 2단계는 읽기뿐이라 provider만 있고 쓰는 곳이 없습니다.
등록 mutation(3단계)과 경품함 조회(4단계)에서 실제로 필요해질 때 도입합니다.
`back_111.md` 스택에서 빼는 것이 아니라 도입 시점만 옮기는 것입니다.

**3) `ShellContext`의 시드 state를 걷어낸다.** `SEED_WINS` / `SEED_USED_CODES` 제거.
3단계 등록 API 전까지 **마이페이지 경품함과 홈 통계가 빈 상태**가 됩니다.
빈 상태 화면은 디자인에 이미 있어 어색하지 않고, 경품 목록만 DB이고 당첨 내역은 가짜인
어중간한 상태를 피할 수 있습니다.

## 3단계 — 리워드 등록 (핵심)

- **TanStack Query Provider 도입** (2단계에서 이월 — 등록 mutation 부터 실제로 필요)
- `POST /api/reward/register`: Zod → Service → Transaction
- 등록 쿼리는 **조건부 UPDATE 1방**으로 (조회 후 갱신 금지)
  ```sql
  UPDATE reward_codes SET userId=?, status='USED', usedAt=?
  WHERE rewardCode=? AND status='UNUSED'
  ```
  영향 행 1 → 성공 / 0 → 이미 사용됨. 락·재시도 불필요
- 전화번호 AES-256-GCM 저장 + HMAC 인덱스 (`crypto.ts` 연결)
- 사용자 생성은 `phoneHash` 기준 upsert (동시 등록 시 unique 충돌 처리)
- 클라이언트 더미 추첨 제거. 1800ms 최소 연출 유지 로직은 재사용
- 이름·전화번호 입력 UI 배치
- **Rate limiting** (위 코드 자릿수 분석에 따라 필수)

**완료 기준**: 같은 코드 2회 → `ALREADY_USED`. 동일 코드 동시 10요청 중 1건만 성공.

배포를 하기로 하면서 "등록 레이트 리밋 생략" 의 전제가 깨졌습니다. 코드 공간은 7,077,888,
유효 코드는 100개라 기대 시도가 약 70,779회 — 제한이 없으면 **초당 100요청으로 약 12분**입니다.

### 1) 사이트 접근 게이트 — `src/lib/site-gate.ts`

패드 QR 을 `https://<사이트>/?k=<토큰>` 으로 만들고, 토큰을 아는 요청만 통과시킵니다.
통과하면 쿠키(7일)를 굽고 주소에서 토큰을 지웁니다.

**비밀번호 로그인 화면을 세우지 않은 이유**: 진입 경로가 QR 이라 참여자 마찰이 0이고,
운영자가 현장에서 비밀번호를 불러줄 일이 없어 유출 경로가 하나 줄어듭니다.

| 항목 | 값 |
|---|---|
| 플래그 | `SITE_GATE_ENABLED` — `"true"`/`"1"` 일 때만 켜짐. **기본 꺼짐** |
| 토큰 | `SITE_ACCESS_TOKEN` |
| 범위 | 정적 자원을 뺀 전 경로. **관리자 화면 포함** |
| 차단 응답 | 페이지 403 안내 화면 / API 401 JSON |
| 쿠키 | `httpOnly` · `SameSite=Lax` · 7일 |

기본값을 **꺼짐**으로 둔 이유는 환경변수를 빠뜨렸을 때 사이트가 통째로 잠기는 것보다
열려 있는 편이 복구가 쉽기 때문입니다. 대신 **켜 놓고 토큰을 빠뜨리면 막습니다** —
켜 달라는 요청을 무시하고 여는 것이 가장 나쁜 결과입니다.

`SameSite=Lax` 는 관리자 쿠키(`Strict`)와 다릅니다. `Strict` 면 메신저·메일에 공유된 링크로
들어온 최초 내비게이션에 쿠키가 붙지 않아 이미 통과한 참여자가 다시 막힙니다.
`Lax` 는 최상위 GET 이동에만 쿠키를 실으므로 교차 사이트 POST 는 여전히 차단됩니다.

> ⚠️ **게이트를 켜면 공모전 심사·포트폴리오 접근이 막힙니다.** 외부에서 봐야 하는 기간에는
> `SITE_GATE_ENABLED="false"` 로 두세요. Next 가 `.env` 변경을 감지하므로 껐다 켜는 데
> 재배포가 필요하지 않습니다(플랫폼에 따라 환경변수 반영 방식은 다를 수 있음).

#### 게이트가 실제로 막는 것과 막지 않는 것 (2026-08-17 명문화)

> 이 절을 적는 이유: 근거가 `site-gate.ts` 주석에만 흩어져 있어서, 나중에
> **"왜 링크를 공유하면 남도 들어와지지?" 를 버그로 오해**할 여지가 있습니다. 버그가 아니라 설계입니다.

게이트가 검사하는 것은 "QR 로 왔는가" 가 **아니라** `?k=` 값이 `SITE_ACCESS_TOKEN` 과
일치하는가 하나뿐입니다(`site-gate.ts:73`). QR 은 그 토큰을 실어 나르는 껍데기이고,
같은 주소를 손으로 쳐도 똑같이 열립니다.

| | 판정 |
|---|---|
| 도메인만 알고 주소창에 입력 | ❌ **차단** (403 안내 화면) |
| 검색엔진 크롤러·무작위 URL 접근 | ❌ **차단** |
| QR 스캔 | ✅ 통과 |
| `?k=` 링크를 손으로 입력 | ✅ 통과 — QR 은 필수가 아님 |
| **참여자가 카톡으로 링크를 전달** | ✅ **통과. 의도된 동작** |
| 한 번 통과한 기기에서 이후 도메인만 입력 | ✅ 통과 (쿠키 7일) |
| `/assets/*.png` 등 정적 자원 | ✅ 게이트 **밖** (matcher 제외, `proxy.ts:171`) |

**링크 공유가 통하는 것은 막지 않기로 한 결과입니다.** 쿠키를 `SameSite=Lax` 로 둔 이유가
바로 그것이고(위 문단), `Strict` 였다면 공유 링크로 들어온 최초 내비게이션이 막혀
**이미 통과한 참여자까지 다시 막혔을** 것입니다.

토큰은 패드마다 다른 값이 아니라 **전원이 공유하는 단일 값**입니다. 따라서 게이트는
사람을 식별하지 못하고, 개별 차단도 불가능합니다. 정확한 성격은 인증이 아니라
**공유 가능한 출입증(bearer token)** 입니다.

> 정확한 문장: ~~"QR 을 찍은 사람만 들어올 수 있다"~~ →
> **"토큰을 가진 요청만 들어올 수 있다. 토큰은 QR 로 배포되고, 한 번 통과한 기기는 7일간 자유롭게 드나든다."**

이 성격은 계획서가 게이트에 기대하는 목적(*"참여자가 특정되는 행사라 공개 엔드포인트일 이유가 없음"*)
에는 부합합니다. 막으려는 대상이 **크롤러·무작위 접근**이지 링크를 받은 사람이 아니기 때문입니다.

#### QR 만드는 법 — 접속 후 주소를 복사하면 안 됩니다

🔴 **가장 틀리기 쉬운 지점입니다.** 게이트는 통과시키면서 **주소에서 `?k=` 를 지우고
리다이렉트합니다**(`proxy.ts:96-98`). 그래서 브라우저로 한 번 들어간 뒤 주소창을 복사하면
**토큰이 빠진 URL** 이 잡히고, 그걸로 만든 QR 은 쿠키가 없는 사람에게 그냥 403 입니다.
게다가 만든 본인은 이미 쿠키가 있어서 **테스트하면 잘 되는 것처럼 보입니다.**

올바른 순서는 접속이 먼저가 아니라 **문자열 조립이 먼저**입니다.

1. `SITE_ACCESS_TOKEN` 값을 그대로 가져와 URL 문자열을 손으로 만든다 — `https://<도메인>/?k=<토큰>`
2. **그 문자열로** QR 을 만든다
3. 검증은 **쿠키가 없는 상태**에서 — 시크릿 창이나 다른 기기로 스캔해 통과하는지 본다

> ⚠️ **온라인 QR 생성기에 붙여넣지 마세요.** 그 URL 은 출입증 전체입니다.
> 오프라인 도구나 로컬 스크립트로 만드세요.

#### 토큰 교체의 대가 — 인쇄 전에 확정할 것

토큰을 바꾸면 **인쇄된 QR 이 전부 죽고, 동시에 이미 통과한 참여자의 쿠키도 전부 무효**가 됩니다.
쿠키에 담기는 값이 원문이 아니라 토큰의 SHA-256 해시라서(`site-gate.ts:68`),
토큰이 바뀌면 `hasGateCookie()` 대조가 어긋나기 때문입니다.

즉 토큰 유출 시 대응책은 교체 하나뿐인데 그 대가가 **패드 재인쇄 + 전 참여자 재진입**입니다.
되돌릴 수 없는 인쇄물에 값을 박는 것이므로 **패드 인쇄는 토큰 최종 확정 후**에 하세요.
6.0.5 파일럿용 토큰을 행사용과 따로 쓰면 인쇄 전까지 마음껏 갈아끼울 수 있습니다.

### 2) 전역 서킷 브레이커 — `POST /api/reward/register`

**실패한 시도만** 셉니다. 성공까지 세면 정상 참여자가 서로의 몫을 깎아먹습니다.
`INVALID_CODE`(존재하지 않는 코드)만 카운트하고, `ALREADY_USED` 는 같은 패드를 두 번 낸
정상 사용자의 신호라 세지 않습니다.

| 키 | 한도 |
|---|---|
| 전역 (분) | 5회 |
| 전역 (시간) | 20회 |
| IP (분) | 5회 |

**전역 카운터가 주 방어선입니다.** IP 기준만으로는 IP 를 돌리면 뚫리는데, 참여자가 10명
안팎이라 정상 실패(오타)가 행사 전체에서 수십 건을 넘지 않아 한도를 극단적으로 낮게 잡아도
정상 사용자는 걸리지 않습니다. 시간당 20건이면 7일간 3,360회 — **1등(1장) 적중 확률 0.05%** 입니다.

> ⚠️ **전역 카운터는 서비스 거부와 맞바꾼 것입니다.** 공격자가 한도를 채우면 정상 참여자도
> 그 창 동안 등록할 수 없습니다. 게이트가 켜져 있으면 외부에서 한도를 채울 수 없으므로
> **게이트가 주 방어선이고 이 카운터는 backstop** 입니다. 게이트를 끈 채 배포한다면 값을 재검토하세요.
>
> 카운터는 프로세스 메모리에 있습니다. 잘못 잠겼을 때는 **재시작하면 즉시 풀립니다.**

  운영자도 QR 링크로 한 번 들어와야 하지만, 예외 경로는 늘어날수록 빠뜨리기 쉽습니다

### 배포 — 대상 선택과 절차 (2026-08-17)

**Railway 를 택합니다.** DB 가 이미 Railway PostgreSQL 이라 같은 프로젝트에 앱 서비스를
붙이는 구성입니다. 근거 셋 중 마지막이 결정적입니다.

1. **`DATABASE_URL` 을 손으로 넣지 않습니다.** 참조 변수 `${{Postgres.DATABASE_URL}}` 로
   내부 주소가 주입됩니다. 로컬이 쓰는 공개 프록시(`*.proxy.rlwy.net`)를 안 거칩니다
2. **`proxy.ts` 가 Node 런타임을 요구합니다.** Next 16 에서 proxy 는 **기본이 Node.js 런타임**이고
   `runtime` 설정 자체가 금지입니다(번들 문서 `proxy.md:223`, 변경 이력 `v16.0.0`).
   `next start` Node 서버면 자명하게 충족됩니다.
   ⚠️ 같은 번들의 `self-hosting.md` 는 *"Proxy 는 Edge 런타임"* 이라고 적고 있는데 **그쪽이 옛 내용**입니다
3. **레이트 리밋이 프로세스 메모리에 있습니다.** 서버리스로 흩어지면 인스턴스마다 카운터가
   따로 생겨 한도가 무력화됩니다. Railway 단일 상시 프로세스면 현재 구현이 설계대로 돕니다

**환경변수** — `DATABASE_URL`(참조 변수) · `PHONE_ENCRYPTION_KEY` · `PHONE_HMAC_SECRET` ·
`ADMIN_PASSWORD_HASH` · `JWT_SECRET` · `SITE_GATE_ENABLED` · `SITE_ACCESS_TOKEN`.

> 🔴 **전화번호 키 두 개는 로컬 `.env` 와 반드시 같은 값이어야 합니다.**
> 같은 DB 를 계속 쓰는데 키가 바뀌면 기존 `phoneEncrypted` 를 복호화할 수 없고
> `phoneHash` 대조도 전부 어긋나, 이미 등록한 사람이 자기 경품함을 못 엽니다.
> `JWT_SECRET` 만 예외입니다 — 바뀌어도 관리자가 다시 로그인하면 그만입니다.
>
> `TEST_ADMIN_PASSWORD` 는 **올리지 마세요.** 테스트 스크립트 전용이고, 운영 환경에
> 비밀번호 원문을 둘 이유가 없습니다.

빌드 파이프라인은 손댈 것이 없습니다. `npm ci` → `postinstall`(`prisma generate`) →
`npm run build` → `npm run start` 순으로 돌고, `next start` 는 플랫폼이 주는 `PORT` 를 씁니다.
`prisma generate` 는 DB 접속이 필요 없어 빌드 단계에서 안전하고, 빌드 자체도 DB 를 읽지
않습니다(사용자 라우트가 전부 정적).

#### 게이트 ON 일 때 관리자 접속

쿠키가 **두 겹**이고 둘 다 있어야 콘솔이 열립니다. 브라우저에서 아래를 한 번 엽니다.

```
https://<도메인>/admin/login?k=<SITE_ACCESS_TOKEN>
```

`proxy.ts` 가 전 경로에서 돌기 때문에 `?k=` 를 **아무 경로에나** 붙일 수 있습니다.
루트로 들어갔다 다시 이동할 필요 없이 로그인 화면으로 직행합니다.

1. `siteGate()` 가 `?k=` 를 `timingSafeEqual` 로 대조 (`site-gate.ts:73`)
2. 통과하면 `site_access` 쿠키를 굽고 **주소에서 `?k=` 를 지운 URL 로 307** (`proxy.ts:96-98`)
3. 재요청된 `/admin/login` 은 `PUBLIC_ADMIN_PATHS` 라 관리자 인증을 건너뜀 (`proxy.ts:38`)
4. 비밀번호 입력 → 관리자 JWT 쿠키 발급

| | 게이트 쿠키 | 관리자 쿠키 |
|---|---|---|
| 이름 | `site_access` | 관리자 JWT |
| 수명 | **7일** | **8시간** |
| SameSite | `Lax` | `Strict` |
| 값 | 토큰의 SHA-256 해시 (원문 아님, `site-gate.ts:68`) | JWT |

- **기기·브라우저마다 따로 해야 합니다.** 노트북에서 했다고 폰이 통과되지 않고, 시크릿 모드도 마찬가지입니다
- **관리자 쿠키가 8시간이라 긴 행사날엔 반드시 한 번 만료됩니다.** 그때 게이트 쿠키(7일)는
  살아 있으므로 비밀번호만 다시 치면 됩니다
- **`?k=` 링크를 즐겨찾기 해두면 복구가 쉽습니다** — 쿠키가 날아가도 다시 열면 재발급됩니다.
  다만 그 북마크 자체가 출입증이니 개인 기기에만 두세요

### 운영 메모 — `catalog.ts` 는 시드 소스입니다

화면과 API 는 `products` **테이블**을 읽습니다. `src/lib/catalog.ts` 를 고쳐도
**`npm run db:seed` 를 돌리기 전까지는 아무 데도 반영되지 않습니다.**
(2026-08-14 에 실제로 설명 문구 3건이 이 이유로 옛 값인 채 남아 있었습니다.)

`seedProducts()` 의 upsert 는 `deletedAt: null` 도 함께 씁니다 — **soft delete 한 상품이
시드 실행으로 되살아납니다.** 카탈로그에서 지운 항목은 DB 에서 사라지지 않는다는 것도 함께 기억하세요.
